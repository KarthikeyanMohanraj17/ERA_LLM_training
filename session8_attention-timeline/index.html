Timeline
    A chronological tour of attention, 2017 → 2026

    How attention actually got here

    Every mechanism below is real, dated, and sourced — check the link at the top of each section if you don't believe a date. They're ordered by when they actually shipped, not by how a textbook would group them. Read it top to bottom and you'll see the field's actual priorities shift over time: first make attention work at all, then make decoding cheaper, then fix position, then make context longer, then bring recurrent state and sparsity back for the parts exact attention can no longer afford.

    2017 – 2018

    Make it work at all

    What forced it
    Nothing yet — this is where the bill starts.
    What got cheaper
    A token could finally read every other token in one step, and training parallelised across the sequence instead of crawling through it.
    The bill it hands on
    Two bills, both immediate: compute growing as T², and a KV cache growing with every generated token. Plus one embarrassment — attention has no idea what order anything is in.
    baselineJun 2017

    Scaled dot-product attention

    Vaswani, Shazeer, Parmar, Uszkoreit, Jones, Gomez, Kaiser, Polosukhin — Attention Is All You Need, arXiv:1706.03762 (Google Brain / Google Research / U. Toronto)

    Before this, a token's vector never learned anything about the other tokens around it. Every mechanism on this page is either this, or a response to a cost this introduced.

    Each token makes three projections of itself: a query ("what am I looking for?"), a key ("what do I contain?"), and a value ("what do I give you if you pick me?"). A token's query is compared against every other token's key with a dot product, the scores are scaled by 1/√d_k so they don't blow up, a causal mask zeroes out anything in the future, softmax turns what's left into weights that sum to 1, and those weights combine the values into one output vector.

    Worked example — one query, two keys, by hand
    Given 2D vectors, d_k = 2: q = [1, 1], k₁ = [1, 0], k₂ = [0, 1], v₁ = 10, v₂ = 20
    1. Dot each key against the query
      q·k₁ = (1×1)+(1×0) = 1.0 q·k₂ = (1×0)+(1×1) = 1.0
    2. Scale by 1/√d_k, so scores don't blow up as d_k grows
      1.0 / √2 = 1.0 / 1.41 = 0.71 (both)
    3. Softmax the scaled scores into weights that sum to 1
      softmax([0.71, 0.71]) = [0.5, 0.5]
    4. Weighted sum of the values
      0.5×10 + 0.5×20 = 15.0
    Answer output = 15.0
    Equal scores → equal weight → the output is just the plain average of v₁ and v₂. Change either key and the weights — and the answer — stop being 50/50.
    Interactive — one query, every intermediate number: score → scale → softmax → weighted sum
    Turn the mask off — attention weight immediately moves onto tokens that haven't happened yet. That's exactly the problem the causal mask exists to solve.
    Two bills this sends: compute grows roughly as T² (every token compares with every other token), and generation needs a growing KV cache — one saved key and value per earlier token, for every active conversation. Everything from here on is field working on one or both of those bills.
    Hands to →
    • Sparse Transformers and FlashAttention attack the T² compute from opposite ends — one approximates it, one refuses to. MQA opens the account on the cache bill.
    Jun 2017

    Sinusoidal positional encoding

    Same paper as above — Attention Is All You Need, arXiv:1706.03762

    Problem
    • Self-attention looks at a set of tokens, not a sequence — it computes the same query/key/value comparisons no matter what order the tokens arrive in.
    • Shuffle "the cat sat" into "sat the cat" and, with no other change, attention scores every pair identically.
    • An RNN gets word order for free just by processing one token after another. A transformer has no such built-in clock.
    • Without fixing this, the model literally cannot tell "dog bites man" from "man bites dog."
    Fixed
    • Add a fixed vector to each token's embedding before the first layer, computed purely from that token's position: PE(pos, 2i) = sin(pos / 10000^(2i/d)), PE(pos, 2i+1) = cos(...).
    • Every dimension pair oscillates at a different frequency, so each position gets a unique, repeatable fingerprint.
    • Nothing here is learned — it's a formula, computed once and reused for every sequence.
    • Because it's just addition, it slots into the existing architecture with no change to the attention computation itself.
    Cost
    • The function can't adapt to the data — every model gets the exact same positional geometry, useful or not.
    • The original paper hoped this would let the model "extrapolate to sequence lengths longer than the ones encountered during training."
    • In practice it doesn't: models trained with sinusoidal PE degrade quickly once you evaluate them past their training length.
    When to choose it
    • Rarely picked for a new model today — later methods extrapolate better.
    • Still worth knowing: RoPE (below) is built directly on this same sin/cos frequency idea, just applied differently.
    Hands to →
    • Two answers pulling opposite ways: learned tables (2018) buy adaptivity and lose extrapolation; ALiBi (2021) gives up learning position at all to buy extrapolation back.
    Worked example — computing PE for one position
    Given d_model = 4 (2 dimension pairs), position pos = 3
    1. Pair i=0 — highest frequency (10000⁰ = 1)
      PE(3,0) = sin(3/1) = sin(3) = 0.141 PE(3,1) = cos(3/1) = cos(3) = −0.990
    2. Pair i=1 — lower frequency (10000^0.5 ≈ 100)
      PE(3,2) = sin(3/100) = sin(0.03) = 0.030 PE(3,3) = cos(3/100) = cos(0.03) = 1.000
    3. Concatenate all four values into one vector
      PE(3) = [0.141, −0.990, 0.030, 1.000]
    Answer PE(3) = [0.141, −0.990, 0.030, 1.000]
    This vector gets added directly to token 3's embedding. Position 4 gets a different, equally fixed vector, computed the exact same way — no training involved.
    Mar 2018

    Relative position representations

    Shaw, Uszkoreit, Vaswani (Google Brain) — Self-Attention with Relative Position Representations, arXiv:1803.02155 (v1 6 Mar 2018). Refined by Transformer-XL (Dai et al., arXiv:1901.02860, Jan 2019) and simplified to a single learned scalar per bucket by T5 (Raffel et al., arXiv:1910.10683, Oct 2019).

    Problem
    • Both position schemes so far are absolute: they answer "where am I in the sequence?" and add that answer to the token before attention runs.
    • But almost nothing in language depends on absolute index. "The cat sat" means the same at position 5 and position 5,000; what matters is that "sat" is two tokens after "the".
    • An absolute scheme has to learn that invariance from data, separately, for every position pair it ever sees — which is exactly why it does not transfer to positions it never saw.
    Fixed
    • Stop adding position to the input. Put it in the query-key comparison instead, as a function of the distance i − j.
    • Shaw et al. add a learned vector per relative offset into the key (and value) before the dot product, with offsets clipped beyond a maximum distance k.
    • T5 later strips this to its cheapest form: one learned scalar per distance bucket, added straight to the attention logit — no vectors, no extra projections.
    • Because it only ever sees distances, the same rule applies at any absolute position, including ones never trained on.
    Cost
    • Shaw's version materialises a distance vector for every query-key pair, which is real extra memory and compute inside the hot loop — the reason later work kept simplifying it.
    • Clipping is a hard ceiling by construction: with T5's buckets, every offset past 128 shares one scalar, so the model cannot tell 300 tokens back from 3,000.
    • It is a replacement, not a bolt-on — the paper reports that combining relative with absolute position gives no further gain.
    When to choose it
    • Any time relative structure is what actually matters and you want it enforced rather than learned — which is most language tasks.
    • T5's scalar-bias form when you want the cheapest possible version and can live with a resolution ceiling; it is still in wide use.
    • Not when you genuinely need absolute index — a model that must reason about "the third item in the list" is fighting the mechanism.
    Hands to →
    • This is the fork in the road. RoPE (2021) gets the same relative property with no learned parameters and no extra compute, by rotating instead of adding — and ALiBi (2021) is precisely T5's scalar bias with the learned value replaced by a fixed slope.
    Worked example — why relative survives a shift and absolute does not
    Given the phrase "the cat sat" appearing twice in one document: once at positions 5–7, once at positions 900–902.
    1. Absolute scheme — what the model sees for the pair ("sat", "the")
      occurrence 1: query pos 7, key pos 5 occurrence 2: query pos 902, key pos 900 two completely different input vectors
    2. It has to learn the same relationship twice, and position 902 may never have appeared in training at all
      nothing links pos 7 to pos 902 except data the model happened to see
    3. Relative scheme — the same pair
      occurrence 1: distance = 7 − 5 = 2 occurrence 2: distance = 902 − 900 = 2 identical input
    Answer one distance value, 2, covers both — and covers position 90,000 too
    This is the entire argument for relative position, and every scheme after it (RoPE, ALiBi, and the extension methods built on RoPE) inherits it. The catch is the ceiling: clip or bucket the distances, as Shaw and T5 both do, and far-apart tokens all collapse to the same value.
    Jun 2018

    Absolute learned positional embeddings

    Radford, Narasimhan, Salimans, Sutskever (OpenAI) — Improving Language Understanding by Generative Pre-Training (GPT-1). Adopted a few months later by BERT (Devlin et al., arXiv:1810.04805, Oct 2018). Footnote: a learned position-embedding table appears even earlier, in a non-attention architecture — Gehring et al., Convolutional Sequence to Sequence Learning, May 2017.

    Problem
    • Careful here — this is not the clean "sinusoidal failed, so someone fixed it" story. Both options were already in the 2017 paper. Vaswani et al. §3.5: "We also experimented with using learned positional embeddings instead, and found that the two versions produced nearly identical results."
    • They picked sinusoidal anyway, for one stated reason: "because it may allow the model to extrapolate to sequence lengths longer than the ones encountered during training." That was a hypothesis, not a measurement.
    • So the real question this entry answers is not "what was broken?" but "which of two equal-scoring options did the field actually adopt, and why?" GPT-1 and BERT chose the learned table — and the reason was pragmatic, not accuracy: a table is one line of code, and extrapolation past the trained length was not a goal anyone was optimising for in 2018.
    Fixed
    • Build an ordinary embedding table, one row per position, sized max_position × d_model — the same construction Gehring et al. had already used for convolutional seq2seq (arXiv:1611.02344, Nov 2016), predating the Transformer entirely.
    • Train it end-to-end alongside the token embeddings — position 5 gets its own learned vector, exactly like word 5 gets its own learned vector.
    • The model is now free to discover whatever positional structure actually helps, instead of being handed one in advance.
    Cost
    • The table only has as many rows as its maximum trained length — say, 4,096.
    • Position 4,097 simply has no row. There's no formula to fall back on the way sinusoidal PE has.
    • Feed the model a longer sequence and it either errors out or reads an untrained, essentially random row.
    When to choose it
    • When you know your maximum sequence length up front and genuinely will not exceed it — a classifier over documents you control, not a chat model.
    • Almost never for a new decoder-only LM today. The 2017 hypothesis turned out to be right in spirit and wrong in detail: sinusoidal does not extrapolate well either (see ALiBi below), but at least it is defined out there. A table is not.
    • The honest verdict on this entry: it is the branch the field took and then backed out of. Everything from RoPE onward is the field deciding that position belongs inside the query-key comparison, not added to the input.
    Hands to →
    • Relative position (2018) drops absolute indices altogether — the road that leads to RoPE and everything after it.
    Worked example — a table lookup, and the row that isn't there
    Given an embedding table sized max_position × d_model = 4,096 × 768, trained on sequences up to 4,096 tokens
    1. Parameter count — this table is trained, so it costs weights
      4,096 rows × 768 numbers = 3,145,728 parameters
    2. Position 4,095 — the last trained row. A lookup, not a calculation
      PE(4095) = table[4095] = [0.13, −0.42, ..., 0.07] ← a real, trained row
    3. Position 4,096 — one token further
      PE(4096) = table[4096] → index out of range
    4. Compare with sinusoidal PE at the same position
      PE(4096, 0) = sin(4096 / 1) = −0.612 ← still just arithmetic
    Answer the table has no row 4,096 — there is nothing to look up, and no formula to fall back on
    This is the whole trade. The sinusoidal formula answers at every position because it computes; the table answers only where it was trained because it remembers.

    2019 – 2020

    The first bills come due

    What forced it
    Sequence lengths hit the point where T² stopped being a rounding error, and serving costs made the KV cache a line item rather than a detail.
    What got cheaper
    Three independent escapes appear within fourteen months: skip most pairs (sparsity), store fewer K/V copies (MQA), or throw out softmax entirely and keep a fixed-size state (linear attention).
    The bill it hands on
    Every one of them is an approximation, and each buys its saving with a different kind of forgetting. Two of the three then go dormant for years.
    Apr 2019

    Sparse Transformers

    Child, Gray, Radford, Sutskever (OpenAI) — Generating Long Sequences with Sparse Transformers, arXiv:1904.10509

    Problem
    • Full self-attention compares every token with every other token — cost grows as the square of sequence length (O(n²)).
    • For text that's painful but tolerable at a few thousand tokens. For raw audio or high-resolution images, sequences run to tens of thousands of steps.
    • At that length, full attention's memory and compute needs become genuinely intractable to train.
    Fixed
    • Don't compute every pair — pick two cheap, complementary patterns and use their union instead.
    • Strided: each token attends to every k-th earlier token, reaching far back cheaply.
    • Local: each token attends to a small nearby window, capturing fine detail.
    • Together they approximate full attention's coverage at O(n√n) — much cheaper, especially as n grows.
    Cost
    • This is an approximation, not full attention — some genuinely relevant token pairs fall outside both the strided and local pattern and are simply never compared.
    • The patterns are hand-designed per data modality, not learned or discovered automatically.
    • Recovering something close to full-attention expressivity typically needs multiple heads running different patterns, not just one.
    When to choose it
    • Very long, structurally regular sequences — images, audio — where a fixed geometric prior about "what should attend to what" is a reasonable bet.
    • Less suited to text, where relevant context can be anywhere and doesn't follow a predictable geometric pattern.
    Hands to →
    • Longformer (2020) keeps the local window and swaps strided reach for explicit global tokens. Then sparsity goes quiet for five years, until NSA (2025) makes the pattern learned instead of hand-drawn.
    Worked example — counting the pairs you actually pay for
    Given 16 tokens, causal mask, stride k = 4, local window = 3. Match the widget below.
    1. Full causal attention — every legal (query, key) pair
      16 × 17 / 2 = 136 pairs
    2. Local branch — each query looks at itself plus the 3 before it
      ≈ 16 × 4 = 64 pairs (fewer near the start, where there is less history)
    3. Strided branch — each query looks back in steps of 4
      ≈ 16 × 4 = 64 pairs, but reaching all the way to token 0
    4. The union, with the overlap counted once
      82 of 136 pairs = 60%
    Answer 82 pairs instead of 136 — and the gap widens fast as n grows
    At 16 tokens 60% is unimpressive. The point is the growth rate: full attention is O(n²), the union is O(n√n). At 4,096 tokens that is roughly a 30× difference in pairs.

    Nov 2019

    Multi-Query Attention (MQA)

    Shazeer (Google) — Fast Transformer Decoding: One Write-Head is All You Need, arXiv:1911.02150

    Problem
    • Generating text one token at a time means re-reading every earlier token's saved key and value at every single layer, every single step.
    • Standard multi-head attention keeps a separate K/V tensor per head, so that's a lot of memory traffic per step.
    • At generation time the GPU isn't waiting on math — it's waiting on moving all that K/V data from memory. This is memory-bandwidth bound, not compute bound.
    • More heads means more bandwidth spent just reloading state, not doing useful work.
    Fixed
    • Keep all the query heads exactly as they were — each still learns its own separate projection.
    • But give them all a single shared set of key and value projections, instead of one K/V per query head.
    • One K/V head to reload per step instead of many — a large, direct cut to memory traffic during generation.
    Cost
    • The paper reports this plainly: "minor quality degradation" relative to full multi-head attention.
    • Every query head is now forced through the same shared K/V — a real bottleneck on how much representational diversity the model can express.
    When to choose it
    • Latency-critical serving where the memory-bandwidth savings matter more than the small quality hit.
    • In practice, more often chosen as the extreme end of GQA's dial (below) than picked on its own from scratch.
    Hands to →
    • GQA (2023) turns this all-or-nothing choice into a dial you can set per deployment.
    Worked example — bytes saved per token, one layer
    Given 8 heads, head_dim = 128, bf16 (2 bytes per number)
    1. MHA cache per token — every head stores its own K and V
      8 heads × (128 K + 128 V) × 2 bytes = 8 × 256 × 2 = 4,096 bytes
    2. MQA cache per token — all 8 query heads share one K/V head
      1 head × (128 K + 128 V) × 2 bytes = 1 × 256 × 2 = 512 bytes
    3. Ratio
      4,096 / 512 = 8×
    Answer 8× less K/V memory traffic per generated token
    That's per token, per layer — multiply by however many layers and tokens the model actually generates to get the real savings.

    Apr 2020

    Sliding window attention — the origin: Longformer

    Beltagy, Peters, Cohan (Allen Institute for AI) — Longformer: The Long-Document Transformer, arXiv:2004.05150

    Problem
    • Document-level tasks — classifying a full article, answering questions over a long passage — need attention over thousands of tokens.
    • Full O(n²) attention at that length is expensive even for an encoder that only needs to run once per document, not once per generated token.
    Fixed
    • Give each token a local, fixed-size window — it only attends to nearby tokens, not the whole document.
    • Window-only attention scales linearly with sequence length instead of quadratically.
    • Add task-specific global attention on a handful of special tokens (like [CLS]) that stay visible to, and see, every other token — so the model still has a place to gather document-wide information.
    Cost
    • A token outside the local window is invisible to that layer, full stop — no direct comparison happens.
    • Long-range dependencies still exist in the document, but now have to propagate indirectly through several stacked layers instead of being read in one attention pass.
    When to choose it
    • Encoder-style, long-document tasks where a few designated tokens can plausibly carry the global-summary role.
    • This is the origin of the sliding-window idea — the decoder/KV-cache version below (Mistral, 2023) applies the same core concept somewhere very different.
    Hands to →
    • Mistral (2023) carries the window into causal decoding, where it caps the KV cache — and immediately hits the eviction problem attention sinks has to fix.
    Worked example — why a window makes the cost linear
    Given a 4,096-token document, window w = 512 (±256), plus 8 global [CLS]-style tokens
    1. Full attention — every token against every token
      4,096 × 4,096 = 16,777,216 pairs
    2. Window attention — each token sees at most w others
      4,096 × 512 = 2,097,152 pairs
    3. Global tokens — each is visible to, and sees, everything
      8 × 4,096 × 2 = 65,536 pairs
    4. Total, and the ratio
      2,162,688 vs 16,777,216 = 12.9% of full attention
    Answer about 7.8× fewer pairs, and the saving grows with document length
    Double the document to 8,192 tokens: full attention quadruples, the window version only doubles — that is the difference between O(n²) and O(n·w).

    Linear attention

    Katharopoulos, Vyas, Pappas, Fleuret (EPFL / Idiap) — Transformers are RNNs: Fast Autoregressive Transformers with Linear Attention, arXiv:2006.16236, ICML 2020

    Problem
    • Softmax normalizes over all the keys a query is compared against — you can't compute what one key contributes without first knowing every other key's score too.
    • That coupling is what forces the O(T²) cost: every query has to be re-compared against every key, every time.
    • It also rules out a tempting shortcut: pre-summarizing everything seen so far into one running total, the way an RNN does.
    Fixed
    • Replace softmax(QKᵀ)V with a kernel feature map φ(Q)φ(K)ᵀV — a similarity function without softmax's shared normalization.
    • Because matrix multiplication associates, this can now be computed as a running sum: a fixed-size state S = Σ φ(kⱼ)vⱼᵀ, updated one token at a time.
    • That's exactly how an RNN's hidden state works — the whole past gets folded into one fixed-size summary as you go.
    • Cost per new token drops from O(T) (compare against everything so far) to O(1) — total sequence cost drops from O(T²) to O(T).
    Cost
    • The kernel feature map only approximates true softmax similarity — a real expressiveness trade, not a free lunch.
    • The entire past is compressed into one fixed-size matrix, so different memories can interfere with and partially overwrite each other.
    • There's no way to go back and read one specific old token exactly — only the blended summary survives.
    When to choose it
    • Very long sequences, where O(T²) softmax attention is the actual bottleneck and some recall loss is an acceptable trade.
    • As a building block inside a hybrid schedule that mixes it with real attention layers (see LightningLM at the end of this timeline).
    Hands to →
    • The delta rule (2021) replaces the additive write with a correction, so new memories stop piling on top of old ones.
    Worked example — the regrouping trick, by hand
    Given 3 tokens seen so far — k₁=0.5,v₁=10 · k₂=1,v₂=20 · k₃=1.5,v₃=30. Query q=2.
    1. Direct route — plug q into every term separately
      q·k₁·v₁ + q·k₂·v₂ + q·k₃·v₃ = 10 + 40 + 90 = 140
    2. Regrouped route — fold keys/values into state S first, no q involved yet
      S = k₁v₁ + k₂v₂ + k₃v₃ = 5 + 20 + 45 = 70
    3. Multiply S by q once
      q × S = 2 × 70 = 140
    Answer both routes = 140 — same number, two different computations
    S never mentions q, so it can be computed once and reused for any future query — that's the whole trick. Play with the widget below to see it break once softmax is switched on.

    2021 – 2022

    Position gets rebuilt — and one bill turns out to be fake

    What forced it
    Absolute position was still bolted onto the input, and none of the schemes survived being evaluated past their training length.
    What got cheaper
    RoPE moves position inside the query-key dot product with no parameters at all. And FlashAttention reveals that much of the "quadratic cost" everyone was approximating away was memory traffic, not arithmetic — recoverable exactly, for free.
    The bill it hands on
    RoPE's base frequency is fixed at training time, which becomes the single biggest obstacle to longer context. The recurrent thread keeps running underneath this era — the delta rule opens it — but nobody can train it fast enough to matter yet.
    Feb 2021

    The delta rule (origin)

    Schlag, Irie, Schmidhuber (IDSIA / USI-SUPSI) — Linear Transformers Are Secretly Fast Weight Programmers, arXiv:2102.11174, ICML 2021

    Correction worth flagging: the delta rule is often attributed to the 2024 "DeltaNet" paper. That paper (below) is a parallel-training algorithm for this exact recurrence — the mechanism itself is three years older.
    Problem
    • Linear attention's write rule is purely additive: S = S + kᵢvᵢᵀ — every new association just gets piled on top of the state.
    • Writing something new never corrects or removes something old, even if the old association is now wrong or stale.
    • Old and new associations sharing the same fixed-size state can interfere with and corrupt each other, with no mechanism to fix it.
    Fixed
    • Reframe the state as a "fast weight" associative memory — an idea echoing 1990s fast-weight-programmer networks.
    • Replace the additive write with a delta-rule-style update: first read what the memory currently returns for this key.
    • Compute the delta — the gap between what it returns and what it should return.
    • Write only that correction, instead of blindly adding the new value on top.
    Cost
    • The correction at each step depends on the memory state left by the previous step — inherently sequential.
    • There's no way (yet, in this 2021 paper) to parallelize that recurrence across the sequence for fast GPU training.
    • That exact gap — training speed — is what the 2024 DeltaNet paper (below) solves.
    When to choose it
    • Whenever the model needs to overwrite or correct what it remembers, not just keep accumulating more on top.
    • This is the conceptual seed for every delta-rule-based recurrent model that follows in this timeline.
    Hands to →
    • DeltaNet (2024) makes the same recurrence trainable in parallel — three years later, because the maths was never the blocker.
    Worked example — two writes to the same memory slot
    Given slot starts at 0. Write 1 wants the slot to hold 40. Write 2 (new information) wants it to hold 55.
    1. Naive additive (linear attention) — write 1
      0 + 40 = 40
    2. Naive additive — write 2
      40 + 55 = 95 (wanted 55 — off by 40)
    3. Delta rule — write 1: read 0, correct toward 40
      delta = 40 − 0 = 40 → write 0 + 40 = 40
    4. Delta rule — write 2: read 40, correct toward 55
      delta = 55 − 40 = 15 → write 40 + 15 = 55
    Answer naive route lands on 95 (wrong); delta rule lands on 55 (exactly right)
    The naive route just keeps piling values on top; the delta rule always corrects toward the target instead of adding to it.

    Apr 2021

    RoPE — Rotary Position Embedding

    Su, Lu, Pan, Murtadha, Wen, Liu (Zhuiyi Technology) — RoFormer: Enhanced Transformer with Rotary Position Embedding, arXiv:2104.09864

    Problem
    • Sinusoidal and learned absolute PE both add a position signal to the embedding before attention runs — position never enters the query-key comparison directly.
    • What actually matters for most tasks is relative distance between tokens, not their absolute position in the sequence.
    • Earlier relative-position schemes (Shaw et al., T5's relative bias) existed, but required modifying the attention computation itself — extra parameters, extra compute.
    Fixed
    • Rotate each query and key vector by an angle proportional to its position, applied right before the dot product.
    • The rotation is multiplicative, not additive — and in a dot product, multiplying two rotated vectors makes their absolute rotations cancel out.
    • What survives is only the difference in rotation — the relative distance: R(iθ)q · R(jθ)k = q · R((j−i)θ)k.
    • No extra parameters, no change to how attention itself is computed — position rides along inside Q and K.
    Cost
    • The base frequency (10000) fixes how position resolution is spread across the head's dimensions.
    • That's a one-time design choice baked in at training time — it isn't adaptive to how far you might later want to extend context.
    • This exact fixed choice is what breaks down at very long context, and is exactly what NTK-aware scaling and YaRN (below) go after.
    When to choose it
    • The default choice for almost any modern decoder-only LLM today.
    • Relative-position-aware, no extra learned parameters, and compatible with linear-attention variants — a genuinely strong all-around default.
    Hands to →
    • Position Interpolation, NTK-aware scaling and YaRN all reshape the rotation to fit a longer window. DroPE (2025) eventually asks whether to keep it at all.
    Worked example — the rotation is the same however you slice it
    Given 2D vectors q = k = [1, 0]. Key at position 2, query at position 8. Rotation angle θ = 0.35 rad per position.
    1. Route A, step 1 — rotate each vector by its own position
      R(2×0.35) k = [0.765, 0.645] R(8×0.35) q = [−0.942, 0.335]
    2. Route A, step 2 — dot the two rotated vectors
      [−0.942, 0.335] · [0.765, 0.645] = −0.505
    3. Route B — rotate only by the distance between them (8−2 = 6 positions → 2.1 rad)

    ALiBi

    Press, Smith, Lewis (UW / FAIR) — Train Short, Test Long: Attention with Linear Biases Enables Input Length Extrapolation, arXiv:2108.12409, ICLR 2022

    Problem
    • Models trained with sinusoidal, or even RoPE, positions degrade sharply once evaluated on sequences noticeably longer than what they trained on.
    • This is the "train short, test long" setting: a model trained at 1,024 tokens, evaluated at 2,048, without ever seeing that length during training.
    • Both prior methods bake in a fixed geometry at training time that simply has nothing defined past that length.
    Fixed
    • Don't add any position signal to the inputs at all — skip embeddings entirely.
    • Instead, subtract a static, non-learned penalty m · distance directly from the pre-softmax attention score.
    • Each head gets its own slope m, geometrically spaced across heads — some heads penalize distance gently, others sharply.
    • Closer tokens get less penalty, farther tokens get more — a built-in, tunable recency bias instead of a learned position signal.
    Cost
    • The penalty grows linearly with distance forever — a strong, fixed recency bias is baked permanently into the mechanism.
    • Tasks that genuinely need to weight far-away evidence as heavily as nearby evidence are fighting the mechanism itself, not just a training gap.
    When to choose it
    • Length extrapolation is the priority, and a recency prior is acceptable — or even desirable for the task.
    • The paper's own headline result: trained at 1,024, evaluated at 2,048, matching a sinusoidal model actually trained at 2,048 — while training 11% faster and using 11% less memory.
    Still open
    • Mostly a dead end, and worth saying so. The recency bias is permanent, and the field went back to RoPE-plus-scaling instead. ALiBi’s lasting contribution is the demonstration that a fixed, non-learned function extrapolates where a learned one cannot — the argument DroPE later takes to its conclusion.
    Worked example — the penalty subtracted from a raw score
    Given head slope m = 0.5. Raw attention score (before ALiBi) between two tokens: 2.0 — same in both cases below.
    1. Tokens 3 apart
      penalty = m × distance = 0.5 × 3 = 1.5 adjusted score = 2.0 − 1.5 = 0.5
    2. Tokens 10 apart, same raw score
      penalty = 0.5 × 10 = 5.0 adjusted score = 2.0 − 5.0 = −3.0
    Answer 0.5 vs. −3.0 — same raw relevance, very different final score
    The gap is purely a function of distance. That's the recency bias, made explicit as one subtraction.
    Interactive — a trained position signal vs. ALiBi's fixed penalty, evaluated past training length
    Flip the toggle to evaluate past the boundary the model was trained up to. The position-embedding curve (red) gets erratic — it never saw those distances during training. ALiBi's penalty (green) doesn't care, because it's a fixed formula applied at every distance, not something the model had to learn.
    Contrast this against the RoPE widget above: RoPE encodes distance inside the query-key dot product and stays neutral about which distance is "better"; ALiBi penalizes distance directly in the score, on purpose, and that fixed formula is exactly what lets it stay predictable past the trained length.

    FlashAttention — the counterexample

    Dao, Fu, Ermon, Rudra, Ré (Stanford) — FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness, arXiv:2205.14135 (v1 27 May 2022). Followed by FlashAttention-2 (Dao, v1 17 Jul 2023) and FlashAttention-3 (Shah, Bikshandi, Zhang, Thakkar, Ramani, Dao, v1 11 Jul 2024) — each a retune of the same idea for a new GPU generation, not a new idea.

    Problem
    • Everything on this page so far treats attention's cost as a maths problem and pays for a cheaper answer with approximation.
    • But a standard attention kernel writes the entire T × T score matrix out to GPU main memory (HBM), reads it back to softmax it, writes it again, and reads it again to multiply by V.
    • At T = 4,096 that matrix is far larger than the values it is computed from, and HBM is roughly an order of magnitude slower than the on-chip SRAM next to the compute units.
    • So a large share of the "quadratic cost" everyone was approximating away was never arithmetic at all — it was memory traffic.
    Fixed
    • Never materialise the T × T matrix. Tile Q, K and V into blocks small enough to fit in SRAM, and compute attention block by block.
    • Keep a running softmax — tracking the max and the sum seen so far, rescaling earlier partial results as new blocks arrive — so the normalisation is exact without ever holding a full row.
    • Recompute the scores in the backward pass instead of storing them, trading a little extra arithmetic for a lot less memory traffic.
    • The output is bit-for-bit the same attention. Nothing is approximated, dropped or summarised.
    Cost
    • The cost is engineering, not quality, and that is the whole point of putting it here.
    • Each version is a hand-written CUDA kernel tied to one vendor's architecture. FlashAttention-3 does not run on A100; FlashAttention-2 leaves H100 hardware idle. The idea is portable; the implementation is not.
    • It makes exact attention affordable for longer, but the cost is still quadratic in sequence length — it moves the wall, it does not remove it.
    • And it raised the bar for everything else on this page: an approximation now has to beat a very fast exact baseline, not a naive one.
    When to choose it
    • Always, if you are running attention on a GPU. This is not a trade-off you weigh — it is the default in every serious framework, and has been for years.
    • It is the honest reference point for judging every other mechanism here: measure your sparse or linear scheme against FlashAttention, not against a naive implementation, or the speedup you report is partly imaginary.
    Hands to →
    • Nothing has to fix this — that is what makes it unusual on this page. But it resets the baseline every later approximation is measured against, which is why NSA (2025) treats hardware alignment as a design constraint from the start rather than an afterthought.
    Worked example — how much of the cost was never arithmetic
    Given one attention head, T = 4,096 tokens, head_dim = 64, fp16 (2 bytes).
    1. The inputs are small
      Q, K, V = 3 × 4,096 × 64 × 2 bytes = 1.57 MB total
    2. The score matrix is not
      4,096 × 4,096 × 2 bytes = 33.55 MB — 21× the size of its own inputs
    3. A naive kernel moves it across HBM four times: write scores, read to softmax, write weights, read to apply to V
      4 × 33.55 MB = 134 MB of traffic, for one head, one layer, one forward pass
    4. FlashAttention never writes it at all — it tiles into SRAM and keeps a running softmax
      traffic ≈ the inputs and output only, ~2 MB
    5. Scale that to a real model: 32 heads × 32 layers
      naive ≈ 137 GB moved per forward pass; tiled ≈ 2 GB
    Answer roughly 60× less memory traffic, for mathematically identical output
    This is why "attention is O(T²) so it must be approximated" was only half true. A large part of the bill was the trip to memory, and that part was recoverable for free. Every approximation on this page that predates 2022 was partly solving a problem that had an exact answer.
    Interactive — where the bytes actually go, tiled vs. naive
    Drag T up. The inputs grow linearly; the score matrix grows quadratically and quickly dwarfs them — and a naive kernel moves it four times. Tiling never creates it, so its traffic tracks the inputs. Both bars compute the same attention: this is the one mechanism on the page that costs nothing in quality.

    Grouped-Query Attention (GQA)

    Ainslie, Lee-Thorp, de Jong, Zemlyanskiy, Lebrón, Sanghai (Google Research) — GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints, arXiv:2305.13245, EMNLP 2023

    Problem
    • MQA's single shared K/V head is the extreme end of the memory-savings spectrum — it saves the most but also costs the most quality.
    • Every deployment wants a different point on that trade-off, but training a separate MQA model from scratch for each one wasn't practical.
    Fixed
    • Make the number of shared K/V heads a tunable dial, not a fixed extreme: split query heads into groups, each group sharing one K/V head.
    • 1 group = MQA. As many groups as query heads = ordinary MHA. Anything in between = GQA.
    • The paper also introduces "uptraining" — converting an existing MHA checkpoint into a GQA model using only about 5% of the original pretraining compute, instead of training from scratch.
    Cost
    • Still a real trade-off, not a free lunch — quality drops somewhat as the number of KV groups shrinks.
    • In exchange you get cache savings and decoding speed that move closer to MQA the fewer groups you use.
    When to choose it
    • The default today for most serving-oriented LLMs (Llama 2's larger sizes, Mistral, Falcon) — a strong, practical baseline.
    • What it doesn't fix: the cache still grows linearly with context length — GQA just lowers the slope, it doesn't flatten the line.
    Hands to →
    • The cache still grows with context, so two answers follow: MLA (2024) compresses what is stored, and sliding window (2023) caps how much is stored at all.
    Worked example — GQA as a dial between MQA and MHA
    Given 8 query heads, head_dim = 128, bf16, 32 layers, 8,192 tokens of context, one user
    1. Cache per token, per layer, for g KV groups
      2 × g × 128 × 2 bytes = 512·g bytes
    2. Whole model, whole context, for each setting of g
      g = 8 (MHA): 512×8 × 32 × 8,192 = 1.07 GB g = 2 (GQA): 512×2 × 32 × 8,192 = 0.27 GB g = 1 (MQA): 512×1 × 32 × 8,192 = 0.13 GB
    3. What the dial actually buys, relative to MHA
      g = 2 → 4× smaller cache; g = 1 → 8× smaller
    Answer one architecture, three points on the same memory-vs-quality line
    The cache still grows linearly with context. GQA lowers the slope of that line; it does not flatten it. That is exactly the limit MLA and sliding windows go after next.

    NoPE — no positional encoding at all

    Kazemnejad, Padhi, Natesan Ramamurthy, Das, Reddy (Mila / IBM Research) — The Impact of Positional Encoding on Length Generalization in Transformers, arXiv:2305.19466 (v1 31 May 2023), NeurIPS 2023. Earlier evidence in the same direction: Haviv, Ram, Press, Izsak, Levy — Transformer Language Models without Positional Encodings Still Learn Positional Information, arXiv:2203.16634 (Mar 2022).

    Problem
    • Six sections of this page have now been spent engineering position signals — and every one of them extrapolates badly in its own way.
    • Nobody had checked the null hypothesis: what happens if a decoder-only model is given no positional encoding whatsoever?
    Fixed
    • Remove the positional encoding entirely and train the decoder anyway.
    • It still works — because a causal mask is itself positional information. Token 5 can see five predecessors and token 900 can see nine hundred; the count of visible tokens uniquely identifies the position, and the model learns to read it.
    • Kazemnejad et al. then compare NoPE against sinusoidal, learned, RoPE, ALiBi and T5-relative on length generalization, and report that NoPE generalizes better than all of them.
    Cost
    • Decoder-only, strictly. Without a causal mask the model is permutation-invariant and NoPE is simply undefined — it cannot be used in an encoder.
    • The evidence is at small scale on reasoning and synthetic tasks, not frontier-scale language modelling.
    • And the practical catch that kept it from taking over: models trained from scratch without positional encoding are harder to train and, per the DroPE authors' own later experiments, consistently underperform RoPE architectures in ordinary in-context quality. Better extrapolation, worse baseline.
    When to choose it
    • Rarely on its own — but it is the control condition that tells you how much your positional encoding is actually buying.
    • In hybrid form it is genuinely deployed: interleaving NoPE layers with RoPE layers is how several 2025 long-context models get their reach.
    • Read this section as the page's honesty check. It is the result that asks whether the six sections before it were necessary at all, and the answer is "less than you would think".
    Still open
    • Largely ignored at the time. DroPE (2025) revives the idea with the fix for its weakness — do not train without positions, train with them and remove them afterwards, so you get RoPE's baseline quality and NoPE's extrapolation.
    Worked example — how a causal mask leaks position for free
    Given a decoder with no positional encoding at all. Ask what each token can distinguish.
    1. Token at index 0 — nothing before it
      attends over 1 position (itself)
    2. Token at index 4
      attends over 5 positions
    3. Token at index 899
      attends over 900 positions
    4. The number of visible tokens is different at every index, and the model can read it off the attention denominator
      count of visible tokens = index + 1 → a unique, exact position signal
    Answer position is recoverable from the mask alone — no encoding required
    This is why removing positional encoding does not simply break a decoder. It also explains the failure mode: the signal is implicit and weak rather than explicit and strong, which is why NoPE-from-scratch trains worse even though it extrapolates better.

    Position Interpolation

    Chen, Wong, Chen, Tian (Meta) — Extending Context Window of Large Language Models via Positional Interpolation, arXiv:2306.15595 — often skipped in summaries of this line of work, but it is the direct predecessor to NTK-aware scaling and YaRN below, and neither reads correctly without it.

    Problem
    • A RoPE model trained at, say, 4K tokens has only ever seen rotation angles up to that length.
    • Simply evaluate it at 32K positions and it produces rotation angles it never learned anything about — garbage, not graceful degradation.
    • Full re-training at the longer length works, but is expensive — the question is whether an existing checkpoint can be extended cheaply instead.
    Fixed
    • Don't extrapolate into unseen positions — compress them into the range the model already knows instead.
    • Linearly rescale every position index by the extension factor before computing the rotation: position 32,000 gets treated the way position 4,000 would have been.
    • Every RoPE dimension is scaled by the exact same uniform factor — simple to implement, no architecture change.
    Cost
    • Uniform compression squeezes every dimension equally — including the high-frequency ones.
    • High-frequency dimensions are exactly what encode fine-grained local position — compress those too hard and nearby-token discrimination degrades.
    When to choose it
    • Simple to implement, and a real improvement over naive extrapolation.
    • Superseded within days by the community's NTK-aware idea below, which compresses non-uniformly instead — treat PI as the first, simplest version of this idea, not the final one.
    Hands to →
    • NTK-aware scaling, weeks later, compresses non-uniformly instead — protecting the dimensions that carry local detail.
    Worked example — compressing position 32,000 down to a trained-length position
    Given model trained at 4,096 tokens. We want to use it at 32,768 tokens.
    1. Compute the extension factor
      32,768 / 4,096 = 8×
    2. Divide the real position by 8 before computing the rotation
      position 32,000 → 32,000 / 8 = position 4,000
    3. Same division applies to every position, including small ones
      position 100 → 100 / 8 = position 12.5
    Answer the model "sees" position 4,000 — a value it actually trained on — for a token that's really 32,000 tokens in
    Every dimension shrinks by the same 8× factor, including the fine-detail ones — that's the flat line in the plot below.
    Interactive — how much rotary resolution survives at each extension factor
    Position Interpolation compresses every dimension by the same amount — the line is flat and both numeric readouts match exactly, whatever the extension factor. That flatness is the whole method, and also the whole complaint against it: dim 0 was resolving adjacent tokens and just lost the same fraction of its resolution as dim 23, which was only tracking coarse range.

    NTK-aware RoPE scaling

    u/bloc97, r/LocalLLaMA — "NTK-Aware Scaled RoPE Allows LLaMA Models to Have Extended (8k+) Context Size Without Any Fine-Tuning and Minimal Perplexity Degradation". Not a peer-reviewed paper — a community post, with closely related independent work by kaiokendev the same month. The exact posting day is secondary-sourced (Reddit's own metadata wasn't directly fetchable); treat late June 2023 as approximate.

    Problem
    • Position Interpolation's uniform compression treats every RoPE dimension the same, but they aren't doing the same job.
    • High-frequency dimensions carry fine local position detail — compressing them as hard as everything else damages exactly the detail that matters most nearby.
    Fixed
    • Relate the problem to Neural Tangent Kernel theory, and scale dimensions non-uniformly instead of uniformly.
    • Compress the low-frequency (long-range) dimensions more — they're less sensitive to the exact position.
    • Leave the high-frequency (local) dimensions close to untouched — they need their resolution preserved.
    Cost
    • Purely heuristic at the time it was posted — no formal error bound, no peer review.
    • Validated only informally, through perplexity numbers the author posted directly in the thread.
    • Required manual tuning per model, since there was no principled formula for exactly how much to compress which dimensions.
    When to choose it
    • A genuine improvement over linear interpolation, and needs no fine-tuning at all.
    • Best treated as a community finding to build on, not a rigorously validated method in its own right — that formalization is exactly what YaRN does next.
    Hands to →
    • YaRN (2023) formalises it, publishes it, and adds the entropy correction the heuristic never had.
    Worked example — uniform vs. non-uniform compression, dimension by dimension
    Given extending context 8×. Two RoPE dimension pairs: dim 0 (wavelength ≈ 6 tokens, fine local detail) and dim 23 (wavelength ≈ 63,000 tokens, coarse range).
    1. Position Interpolation — every dimension divided by the same 8
      dim 0 keeps 1/8 = 12.5% of its rotation speed dim 23 keeps 1/8 = 12.5%
    2. What that costs dim 0 in practice
      wavelength 6 → 48 tokens: two tokens 1 apart now differ by 1/48 of a turn instead of 1/6
    3. NTK-aware — scale by dimension, with d running 0 → 1 across the pairs
      kept(d) = 1 / (1 + (8−1)·d) dim 0 (d=0): 1 / 1 = 100% dim 23 (d=1): 1 / 8 = 12.5%
    Answer dim 0 keeps all its local resolution; dim 23 absorbs the entire 8× compression instead
    Same total compression budget, spent where it hurts least. The long-wavelength dimensions were never resolving single tokens anyway — they can afford it, and the local ones cannot.

NTK-aware bends it: dim 0 (short wavelength, local detail) stays near 100% even at 8×, and dim 23 (long wavelength, coarse range) absorbs almost all of the compression instead.     YaRN

    Peng, Quesnelle, Fan, Shippole — YaRN: Efficient Context Window Extension of Large Language Models, arXiv:2309.00071, ICLR 2024 ("Yet another RoPE extensioN")

    Problem
    • Linear interpolation needed substantial fine-tuning to recover quality at the extended length.
    • The informal NTK-aware idea needed less fine-tuning, but as an unpublished heuristic it still left a real, unexplained performance gap versus a model natively trained at that length.
    Fixed
    • Formalize "NTK-by-parts" — a refined, published, mathematically grounded version of bloc97's non-uniform interpolation idea.
    • Add a correction to the attention "temperature" — a fix for a softmax-entropy mismatch that interpolation quietly introduces on its own.
    • Together, these close most of the gap that the community heuristic left open.
    Cost
    • One more hyperparameter to get right — the temperature correction.
    • Still benefits from fine-tuning at the target length, just far less of it than linear interpolation needed.
    • Validated primarily on LLaMA-family RoPE models — not a universal guarantee across every architecture.
    When to choose it
    • Extending an existing RoPE model's context cheaply.
    • The paper reports comparable results to Position Interpolation with roughly 10× fewer tokens and 2.5× fewer training steps.
    Hands to →
    • In production, plain base-frequency scaling (Llama 2 Long, arXiv:2309.16039, Sep 2023) largely won — by accepting the very thing YaRN tried to avoid: just continue pretraining at the longer length. DroPE attacks the premise instead.
    Worked example — why interpolation needs a temperature fix
    Given 8 attention scores, softmax taken over all eight. Interpolation shrinks the spread between them, because compressed positions produce closer rotation angles.
    1. Before extension — scores are well separated
      scores = [4.0, 2.0, 1.0, 0.5, 0, 0, 0, 0] softmax → top weight ≈ 0.78
    2. After 8× interpolation — the same scores, squeezed toward each other
      scores ≈ [1.6, 0.8, 0.4, 0.2, 0, 0, 0, 0] softmax → top weight ≈ 0.36
    3. Attention got flatter — higher entropy, less decisive, without anything about the content changing
      YaRN divides the scores by a temperature t < 1 before softmax to undo it scores / 0.5 = [3.2, 1.6, 0.8, 0.4, 0, 0, 0, 0] → top weight ≈ 0.66
    Answer the temperature correction restores the sharpness that interpolation quietly washed out
    This is the part NTK-aware scaling never addressed. It fixed which dimensions get compressed; YaRN also fixed what compression does to the softmax itself.
    Interactive 1 of 2 — NTK-by-parts: decide per dimension, using its wavelength
    Not a smoother version of NTK-aware — a different rule. YaRN asks how many times each dimension's wavelength fits inside the trained context. Fits many times over (r > 32) → it is resolving nearby tokens, leave it completely alone. Has not completed one turn in the whole window (r < 1) → it only carries coarse range, interpolate it fully. In between, ramp. That is why this curve is flat-then-falling rather than a smooth decay: it is piecewise by construction.
    Interactive 2 of 2 — the temperature fix, the part NTK-aware never had
    Start at t = 1.00: the bars sit well below the dashed outline. Nothing about the content changed — compressing positions alone made attention hedge. Drag t down to 0.40 and the bars land exactly on the outline, because the temperature cancels the squeeze precisely. This is the entropy correction YaRN adds on top of the by-parts interpolation, and it is the whole reason YaRN needs less fine-tuning than the community heuristic it formalises.

    Sliding window attention — the decoder application: Mistral 7B

    Mistral AI — official blog announcement (Sep 27, 2023); paper: Jiang et al., Mistral 7B, arXiv:2310.06825 (Oct 10, 2023)

    Problem
    • By 2023, decoder-only LLMs serving long, ongoing conversations needed a KV cache that stops growing — an unbounded cache means unbounded memory.
    • Longformer's local-window idea already existed, but it was built for encoders, not causal, KV-cached autoregressive generation.
    • Nobody had wired the same core idea into the specific setting of generating one token at a time with a growing cache.
    Fixed
    • Each layer attends only to the previous 4,096 tokens, no matter how long the conversation has gotten.
    • The KV cache becomes a fixed-size rotating buffer — old entries get evicted as new ones come in — instead of a list that keeps growing with every generated token.
    • Compute per step is now O(window · seq_len) instead of growing without bound, and memory is capped.
    Cost
    • Same information-loss trade as Longformer's origin: anything outside the window is invisible to that layer, period.
    • Without something like attention sinks (next section), evicting the very first tokens of the conversation can destabilize generation quality.
    When to choose it
    • Serving long or streaming conversations, where a bounded, predictable memory footprint matters more than exact access to the entire history.
    Hands to →
    • Attention sinks, two days later, diagnoses exactly why evicting the first tokens breaks generation — and fixes it for the price of four cached tokens.
    Worked example — the cache that stops growing
    Given 32 layers, 8 KV heads, head_dim = 128, bf16, sliding window W = 4,096
    1. Cache per token across the whole model
      2 × 32 layers × 8 heads × 128 × 2 bytes = 131,072 bytes = 0.13 MB
    2. Unbounded cache at 32K and at 128K of conversation
      32,768 × 0.13 MB = 4.3 GB 131,072 × 0.13 MB = 17.2 GB
    3. Sliding-window cache — capped at W entries, whatever the length
      4,096 × 0.13 MB = 0.54 GB at 32K 4,096 × 0.13 MB = 0.54 GB at 128K 4,096 × 0.13 MB = 0.54 GB at 10M
    Answer 0.54 GB per user, flat — memory stops being a function of conversation length
    The line stops climbing. That is a different kind of win from GQA, which only lowered the slope. The bill: anything older than 4,096 tokens is gone from that layer.

That flat number is the whole difference from GQA, which only made the growing line grow more slowly. The price: a red-ring token is gone from this layer, not merely unattended-to this step.

    Attention sinks / StreamingLLM

    Xiao, Tian, Chen, Han, Lewis (MIT / Meta AI / CMU / NVIDIA) — Efficient Streaming Language Models with Attention Sinks, arXiv:2309.17453, ICLR 2024

    Problem
    • A naive fixed-size sliding-window cache (like Mistral's) collapses in quality once the very first few tokens slide out of the window — even though the total sequence length itself is fine.
    • The paper traces this to softmax: attention weights must sum to 1 across whatever's attended to, so the model needs somewhere to "dump" attention it doesn't want to allocate elsewhere.
    • Under a causal mask, the earliest tokens are visible to — and trained as a target by — nearly every later position, so the model learns to lean on them as that dumping ground.
    • Evict those first tokens once the window slides past them, and that dumping ground disappears, and generation quality collapses with it.
    Fixed
    • Always keep the key/value of a small number of initial "sink" tokens permanently cached — often just 4 — regardless of what the sliding window is currently covering.
    • They ride alongside the normal sliding window instead of getting evicted with everything else that falls behind it.
    • This restores generation stability for streaming, effectively-infinite-length generation, with no fine-tuning required.
    Cost
    • It's a stability fix, not a way to recover true long-range recall — content evicted from the sliding window is still gone for good.
    • The price is a small, constant memory overhead: just a handful of extra cached tokens.
    When to choose it
    • Any deployment already using a bounded sliding-window KV cache for long or streaming generation.
    • Close to a strict improvement at near-zero extra cost — there's little reason not to add it once you're already windowing.
    Still open
    • Still open as stated. Sinks restore stability, not recall — evicted content is gone for good. Recovering long-range recall cheaply is what the whole sparse-attention line (NSA, DSA) exists to do.
    Worked example — where the attention mass goes when the sinks leave
    Given a query attending over 4 sink tokens and 8 window tokens. Softmax weights must sum to exactly 1.
    1. With sinks — the model parks weight it does not want to spend
      4 sinks → 0.55 total 8 content → 0.45 total, so ≈ 0.056 each
    2. Evict the sinks — that 0.55 does not vanish, softmax renormalises
      8 content → 1.00 total, so 0.125 each
    3. What each content token now receives
      0.125 / 0.056 = 2.2× the weight the model intended to give it
    Answer every content token gets more than double its intended weight, purely from removing the dump
    Nothing about the content changed. The distortion is an accounting artifact of softmax having to sum to 1, which is why keeping 4 tokens — a constant, not a per-token cost — fixes it.
    Interactive — where a token’s attention mass goes, with and without the sinks
    Softmax has no choice: the weights must sum to 1. Toggle the sinks off — that 55% doesn’t disappear, it gets redistributed onto real content tokens, which then carry weights the model never trained to give them. The fix costs 4 permanently cached tokens, a constant that never grows with the conversation.
    2024 – 2025

    Recurrent state and sparsity both return

    What forced it
    Retrofits had run out of room. The cache-versus-context line still climbed, and no amount of rescaling made a 2023-era model a million-token model.
    What got cheaper
    The two ideas abandoned in 2020 come back, both fixed. Recurrence gets trainable in parallel (DeltaNet) and gets proper forgetting (Gated DeltaNet, Mamba-2). Sparsity gets learned instead of hand-drawn, and hardware-aligned (NSA, DSA). MLA changes what a cache entry is.
    The bill it hands on
    Bounded state cannot do exact recall and no amount of gating fixes that; learned selection is still an approximation that can miss. Both point at the same answer — mix layer types rather than pick a winner.

    Multi-head Latent Attention (MLA)

    DeepSeek-AI — DeepSeek-V2: A Strong, Economical, and Efficient Mixture-of-Experts Language Model, arXiv:2405.04434

    Problem
    • The DeepSeek-V2 paper states it directly: GQA and MQA reduce the KV cache, but their performance "does not match MHA."
    • Both save memory the same way — by storing fewer copies of the same kind of K/V vectors — and that's exactly what costs quality.
    Fixed
    • A mechanistically different idea, not a rebrand of GQA: perform low-rank joint compression of keys and values together into one small latent vector per token.
    • At attention time, that latent is expanded back out into full-size K and V on demand.
    • What's cached is only the small latent — not fewer copies of full-size vectors, but one compressed representation that gets reconstructed.
    Cost
    • Real architectural complexity — extra up/down-projection matrices that GQA/MQA don't need.
    • RoPE needs a separate, decoupled handling scheme, since rotation doesn't commute cleanly with the compression.
    • More moving parts overall than "just share some heads."
    When to choose it
    • When you want GQA-or-better cache savings without GQA's quality hit.
    • The paper reports MLA matching or beating full MHA quality at a cache footprint comparable to roughly 2.25-group GQA.
    Hands to →
    • Nothing later removes MLA’s complexity — it is the price of admission, and the field paid it. What follows is sparsity: compress what you store, then stop reading most of it too.
    Worked example — cache footprint, GQA vs. MLA
    Given 8 attention heads, head_dim = 128. GQA with 2 KV groups. MLA with a latent size of 512 (DeepSeek-V2's actual choice).
    1. GQA cache per token — 2 groups, each a full-size K and V
      2 × (128 K + 128 V) = 2 × 256 = 512 numbers
    2. MLA cache per token — just the compressed latent
      512 numbers (reconstructed into full 8-head K/V only when attention actually runs)
    3. Full MHA cache per token, for reference
      8 × 256 = 2,048 numbers
    Answer GQA and MLA cache about the same 512 numbers here
    But MLA's reported quality matches full MHA (2,048 numbers), while GQA's 512-number cache comes with a real, measured quality cost. Same size, different trade.

    Mamba-2 — the other branch, and where it meets this one

    Dao, Gu — Transformers are SSMs: Generalized Models and Efficient Algorithms Through Structured State Space Duality, arXiv:2405.21060 (v1 31 May 2024). Predecessor: Gu, Dao — Mamba: Linear-Time Sequence Modeling with Selective State Spaces, arXiv:2312.00752 (Dec 2023).

    Problem
    • Linear attention and the delta rule arrived at a fixed-size recurrent state by simplifying attention. State-space models arrived at the same place from classical signal processing, and for years the two literatures barely spoke.
    • Mamba (Dec 2023) made state-space models genuinely competitive by letting the state-transition parameters depend on the input — "selectivity" — but its hardware-efficient scan was intricate and bespoke.
    • Meanwhile the delta-rule line had a forgetting problem it could not solve, and the SSM line had a targeted-correction problem it could not solve.
    Fixed
    • Prove the two are the same object. The paper's "structured state space duality" shows selective SSMs and a class of linear attention are two views of one computation.
    • Restrict the state transition from Mamba-1's per-channel diagonal to a single scalar times identity — which makes the whole recurrence expressible as a matrix multiply.
    • That one restriction lets Mamba-2 run on ordinary tensor cores at 2–8× Mamba-1's speed, instead of needing a hand-written scan.
    • It also makes the two branches directly comparable, which is what lets the next paper combine them.
    Cost
    • The scalar-identity restriction is a real loss of expressiveness against Mamba-1's per-channel state — the paper trades selectivity for hardware alignment, and that is the honest framing.
    • Still a bounded state, with all that implies: it cannot retrieve an arbitrary earlier token exactly, which is why every serious deployment ended up hybrid rather than pure.
    • The duality result is mathematically tidy but it did not end the argument — it reframed it as "how many exact-attention layers do you actually need?", which nobody has answered from first principles.
    When to choose it
    • As a backbone layer when the workload is long and mostly sequential, and exact recall of one specific distant token is rare.
    • Practically never on its own at frontier scale. The lesson every hybrid on this page encodes is that a few attention layers among many recurrent ones beats either extreme.
    Hands to →
    • Gated DeltaNet (Dec 2024) fuses Mamba-2's decay gate with the delta rule's targeted correction. Its title says so outright: "Gated Delta Networks: Improving Mamba2 with Delta Rule". Without this section that title is unreadable.
    Worked example — why a fixed state is a hard recall ceiling
    Given a recurrent layer with a state of 256 numbers in bf16, processing 100,000 tokens.
    1. What the state can hold, total
      256 × 2 bytes = 512 bytes — constant, whatever the sequence length
    2. What an attention KV cache would hold for the same span
      100,000 tokens × 512 bytes/token ≈ 51 MB
    3. Compression ratio the recurrent layer is implicitly asking for
      51,200,000 / 512 = 100,000×
    4. So the per-token budget in the state is
      512 bytes ÷ 100,000 tokens ≈ 0.005 bytes per token
    Answer the state cannot store per-token detail at all — it can only store a summary
    This is not a tuning problem, it is arithmetic, and it is why the field converged on hybrids rather than picking a winner. A fixed state is exactly the right tool for "what has this document been about" and exactly the wrong one for "what was the account number on page 40".

    DeltaNet — parallelizing the delta rule

    Yang, Wang, Zhang, Shen, Kim — Parallelizing Linear Transformers with the Delta Rule over Sequence Length, arXiv:2406.06484, NeurIPS 2024

    Problem
    • Schlag et al.’s 2021 delta-rule recurrence (above) has real correction math, but it's inherently sequential — each step needs the previous step's result.
    • That rules out parallelizing it across the sequence dimension on a GPU or TPU.
    • Without parallel training, it's impractical to scale the delta rule up to production-sized models.
    Fixed
    • Keep the delta rule's math exactly as it was — nothing about the correction itself changes.
    • Introduce a hardware-efficient, chunk-parallel training algorithm using a memory-efficient Householder-matrix-product representation of that same recurrence.
    • Tokens inside one chunk can now be processed together instead of one at a time, with far fewer sequential steps overall.
    • Scaled successfully to 1.3B parameters / 100B tokens, beating Mamba and GLA at the time.
    Cost
    • Real algorithmic complexity — the chunked WY/Householder representation is intricate machinery compared to the conceptually simple original recurrence.
    • Still a bounded-state recurrent model underneath: recall is limited by the state's fixed size, exactly as it was for Schlag et al.'s original.
    When to choose it
    • Whenever you want the delta rule's correction behavior at production training scale.
    • This — not Schlag et al.'s 2021 paper — is what people mean today when they say "DeltaNet" in most model cards.
    Hands to →
    • Gated DeltaNet (2024) adds the fast, coarse forgetting the delta rule cannot do on its own.
    Worked example — where the chunk-parallel speed-up comes from
    Given a training sequence of 4,096 tokens, chunk size C = 64
    1. The 2021 recurrence — every token waits for the one before it
      4,096 sequential steps
    2. Chunked — tokens inside a chunk are computed together; only chunks are sequential
      4,096 / 64 = 64 sequential steps
    3. Reduction in sequential depth
      4,096 / 64 = 64×
    Answer 64× fewer steps that must happen one after another — the same total arithmetic, differently ordered
    Total FLOPs barely change. What changes is how much of the work a GPU can do at once, and that is what makes the delta rule trainable at scale.
    Interactive — sequential steps vs. chunk-parallel steps to train on the same tokens
    Drag the chunk size up from 1 — the correction math per token never changes (see the widget two sections up), only how many tokens get batched into one parallel step. That's the entire contribution of this paper: same recurrence, far fewer sequential steps needed to train it.

    Gated DeltaNet

    Yang, Kautz, Hatamizadeh (NVIDIA) — Gated Delta Networks: Improving Mamba2 with Delta Rule, arXiv:2412.06464, ICLR 2025

    Problem
    • The delta rule alone gives precise, targeted corrections — it can fix one specific wrong memory — but has no efficient way to do wholesale forgetting.
    • Long-context tasks accumulate a lot of stale state that's no longer useful, and correcting it one association at a time is too slow.
    • Mamba2-style gating solves the opposite problem: fast, coarse forgetting, but with no targeted correction of what's kept.
    Fixed
    • Combine both mechanisms in one recurrence instead of picking one.
    • A data-dependent decay gate α can erase state quickly — coarse, fast forgetting.
    • A write-strength β then governs the delta-rule-style correction on top of whatever survives the decay — targeted, precise updates.
    Cost
    • Another set of learned gating parameters, and another axis of complexity on top of the delta rule's own machinery.
    • Still a finite-state recurrent model underneath — gating helps manage that finite state, it doesn't remove the fundamental size limit.
    When to choose it
    • Long-context recurrent-state models where stale information genuinely needs to be forgotten, not just diluted by new writes.
    • This is the D-layer building block LightningLM (last section) uses.
    Hands to →
    • Bounded state is not fixable inside a recurrent layer, so the answer is architectural — interleave a few exact-attention layers among many recurrent ones. That is the hybrid stack in the case study that closes this timeline, and the shape most 2025–26 long-context models converged on.
    Worked example — decay first, then correct
    Given memory slot holds 80. New information wants it to hold 30. Decay gate α = 0.25 (keep a quarter, forget the rest).
    1. Delta rule alone — correct straight from 80 to 30
      delta = 30 − 80 = −50 → write 80 + (−50) = 30
    2. Gated — decay the old state first
      decayed = 80 × 0.25 = 20
    3. Then apply the delta rule to whatever survived
      delta = 30 − 20 = 10 → write 20 + 10 = 30
    4. Both land on 30. The difference is what happened to everything else in the state
      α = 0.25 shrank every stale association by 4×, in one multiply
    Answer same target hit either way — but gating also wiped the stale state the delta rule would have had to correct one association at a time
    α is coarse and fast: it forgets everything at once. β-weighted delta writes are precise and slow: they fix one thing exactly. Gated DeltaNet keeps both because they solve opposite problems.

    Native Sparse Attention (NSA)

    Yuan, Gao, Dai, Luo, Zhao, Zhang et al. (DeepSeek-AI, Peking University, University of Washington) — Native Sparse Attention: Hardware-Aligned and Natively Trainable Sparse Attention, arXiv:2502.11089, ACL 2025

    Problem
    • Most prior sparse-attention schemes were bolted onto an already-trained dense model as an afterthought.
    • Many also used sparsity patterns that didn't align with how GPU kernels actually execute — leaving real speedups on the table even when the pattern itself was sound.
    Fixed
    • Run three parallel branches per query, trained end-to-end from scratch — not retrofitted onto an existing model.
    • Coarse-grained compressed attention over blocks — cheap, broad coverage.
    • Fine-grained selected attention over the top-scoring blocks — precise, targeted detail.
    • A sliding-window local branch — nearby context, always available.
    • All three are designed hardware-aligned from the start, so the theoretical savings actually show up as real speedups.
    Cost
    • Compression genuinely loses token-level detail — one summary now speaks for several tokens at once.
    • Block selection can miss a genuinely relevant block if its cheap summary undersells it.
    • Being "natively trainable" cuts both ways: you can't simply retrofit this onto an existing dense checkpoint the way some earlier sparse schemes could.
    When to choose it
    • Training a new long-context model from scratch, where hardware efficiency at training time matters as much as inference-time savings.
    Hands to →
    • DSA (2025) makes the same idea retrofittable onto an already-trained model, and selects individual tokens rather than whole blocks.
    Worked example — what the three branches cost together
    Given 64 blocks of 64 tokens (4,096 tokens total). NSA selects k = 8 blocks, plus a 2-block local window.
    1. Full attention — read every block in detail
      64 blocks read at full cost
    2. Compressed branch — every block, but one coarse summary each
      64 summaries ≈ 1 block of cost (that is what compression buys)
    3. Selected branch — the top-8 blocks, read fully
      8 blocks at full cost
    4. Sliding-window branch — the last 2 blocks, always
      2 blocks at full cost
    5. Add them up
      ≈ 1 + 8 + 2 = 11 blocks vs 64 = 17% of the cost
    Answer roughly 6× cheaper, with the local window guaranteeing nearby context is never lost to a bad score
    The three branches are not alternatives — they are summed. Each covers a failure mode of the others: compression misses detail, selection can misrank, the window can't reach far.
    Interactive — three branches over the same blocks: compressed, selected, sliding window
    compressed reads every block, but only as one coarse summary each — cheap and broad. selected reads the top-k blocks in full detail. sliding window always reads the last few blocks, so nearby context is never gambled on a score. The three outputs are summed. Drag k to 16 and the middle branch stops being selective at all — that's just dense attention again.

    DeepSeek Sparse Attention (DSA)

    DeepSeek-AI — DeepSeek-V3.2-Exp release notes, built via continued training on top of DeepSeek-V3.1-Terminus (Sep 29, 2025)

    Problem
    • NSA's Cost above says it plainly: being natively trainable means you cannot retrofit it onto a model you have already trained. DeepSeek had V3.1-Terminus in production and wanted sparse attention in it, not in a successor.
    • NSA selects whole blocks. A block is a blunt unit — one critical token inside an otherwise dull block gets averaged into invisibility by the block's summary score.
    • And the ranking step itself has to be genuinely cheap, not just the attention step it feeds into, or selectivity pays for itself and no more.
    Fixed
    • Add a small, cheap "lightning indexer" — a few heads with ReLU scoring, run in FP8 — that computes a relevance score between the current query and every preceding token.
    • A fine-grained token selector then keeps the top-k individual tokens — k = 2,048 in V3.2-Exp — and only those KV entries are read at full cost.
    • This is the difference from NSA: NSA selects blocks, DSA selects tokens. Finer granularity means a single relevant token can no longer be hidden inside a block whose average score was low.
    • Shipped as a production refinement of an existing model rather than a from-scratch research architecture — installed onto V3.1-Terminus by continued training, not trained in from the start.
    Cost
    • The indexer's ranking is itself an approximation, not a guarantee. A token it underrates is a token the model never reads, however relevant it actually was.
    • Token-level selection is finer but not free: scoring every token individually is more index work than scoring one summary per block, so the indexer has to be kept genuinely cheap or the saving evaporates.
    • Fixed k means the cost stops scaling with context, but so does the amount the model can attend to — at 128K context with k = 2,048, the model reads under 2% of what it could.
    When to choose it
    • Serving a very long context cheaply, when you already have — or can train — a good, cheap relevance signal.
    • The indexer only has to be good enough to rank candidates, not good enough to attend to them itself.
    Still open
    • Open, and actively contested. Whether learned sparse selection beats dense attention at frontier scale is still being argued in public, and the answer keeps moving — labs have shipped sparse attention, reverted to dense, and gone back again inside a single year.
    Worked example — the indexer only has to be cheap enough to rank
    Given 64 blocks. Full attention costs d = 512 per block; the lightning indexer is low-rank at r = 32.
    1. Score every block with the cheap indexer
      64 blocks × 32 = 2,048 units
    2. Read the top 8 blocks at full cost
      8 blocks × 512 = 4,096 units
    3. Total, against dense attention over all 64 blocks
      2,048 + 4,096 = 6,144 vs 64 × 512 = 32,768
    4. Ratio
      6,144 / 32,768 = 19%
    Answer about 5× cheaper — ranking is a third of the new bill (2,048 of 6,144), but only 6% of what dense would have cost
    This is why the indexer being an approximation is acceptable. It never has to be as good as attention, only good enough to put the right blocks in the top 8 — and it costs 16× less per block to try.

    DroPE

    Gelberg, Eguchi, Akiba, Cetin (Sakana AI) — Extending the Context of Pretrained LLMs by Dropping Their Positional Embeddings, arXiv:2512.12167 (v1 13 Dec 2025) — "DroPE" is the backronym coined inside the abstract, not part of the title

    Problem
    • RoPE's rotation formula is just math — it can be evaluated at any position you like, with no error.
    • That doesn't mean the model behaves sensibly there. A model trained only up to 8K tokens never learned what rotation patterns beyond that actually mean.
    • The function keeps producing numbers regardless — those numbers just correspond to nothing the model was ever trained to interpret.
    • Every scaling/interpolation fix so far (PI, NTK-aware, YaRN) works by reshaping the rotation itself. None of them ask whether the rotation is the right thing to keep at all.
    Fixed
    • Pretrain normally with RoPE, exactly as usual — nothing changes about training.
    • Afterward, rather than scaling or interpolating the rotation, drop the positional embeddings entirely.
    • Run a brief recalibration phase at the original training context length to let the model adjust to operating without them.
    • This restores the model's original in-context perplexity, while substantially improving how well it generalizes to longer lengths — without a full long-context fine-tuning run.
    Cost
    • Validated by Sakana on standard RoPE transformers up to 7B parameters.
    • It's a recent technique — its behavior at much larger, architecturally different models (hybrid recurrent + sparse-attention stacks) is a live open question.
    • Not yet independently established at that scale by anyone outside the original paper.
    When to choose it
    • Extending an already-trained RoPE model's usable context without committing to a full long-context training run.
    Hands to →
    • LightningLM 0.1V applies it well past the 7B Sakana themselves tested — which is exactly where a young technique earns or loses trust.
    Worked example — the formula answers; the model does not
    Given a RoPE model trained to 8,192 tokens. One rotary dimension with θ = 0.01 rad per position. We evaluate at position 40,000.
    1. Inside training — a rotation the model saw thousands of times
      angle(8000) = 8000 × 0.01 = 80.00 rad 80.00 mod 2π = 4.602 rad → a specific, learned direction
    2. Far outside training — the arithmetic is just as valid
      angle(40000) = 40000 × 0.01 = 400.00 rad 400.00 mod 2π = 4.159 rad → a perfectly ordinary number
    3. The problem is not the number, it is what produced it
      4.159 rad at position 40,000 4.160 rad at position 416 the same rotation twice — and the model only ever trained on the second
    Answer RoPE never errors out past its trained length — it returns confident, meaningless geometry
    PI, NTK-aware and YaRN all reshape that rotation so it lands somewhere the model recognises. DroPE asks a different question: if the signal is unreliable out here anyway, is it worth keeping at all?

Without DroPE, quality holds inside the trained length then degrades once you push past it — those positions were never seen in training. With DroPE, a brief recalibration after dropping the positions costs a little quality right at the boundary and then stays flat well beyond it.     LightningLM 0.1V — DroPE applied at 120B scale

    Shravan (The School of AI) — Reversible Foundations: Training a 120B Sparse MoE through State-Preserving Scaling, arXiv:2606.07404

    Two things this is commonly confused about. The version string is 0.1V — "V4" names the training programme that produced it, not a model version, so "LightningLM V4" is wrong. And DroPE was not invented here: it is Sakana AI's technique, applied downstream at a far larger scale than Sakana's own published experiments reached. What is new here is the assembly, not the parts.

    The architecture repeats an eight-layer motif, D D D G D D D G, where D is a Gated DeltaNet-style fixed-state layer and G is a sparse-attention layer — six D's compressing history cheaply, two G's giving the model a chance to read selected earlier tokens directly. A "Memory Stream" carries one fixed-size, model-width summary vector across chunk boundaries (written with a stop-gradient, read with a small learned gate), so state from an earlier chunk isn't simply discarded. Positional recalibration via DroPE was applied before the final annealing stage of training (§5.3). Every architectural claim in this paragraph was checked against the paper's own text: the motif is §3.1/Table 1, the Memory Stream is §3.2.

    One thing worth stating plainly, because it is the kind of error this page exists to catch: the paper never sweeps the D:G ratio. Table 5 holds it at 3:1 for every stage it trains — 6 D : 2 G at eight layers, 15 D : 5 G at twenty. The widget below therefore shows arithmetic (only G layers cache, so cache scales with the G count), not a measured curve, and it says so on the canvas.

    Worked example — what D D D G D D D G buys
    Given an 8-layer motif where only the G (sparse-attention) layers carry a KV cache. Compare 2 G's per 8 against all-attention.
    1. All-attention baseline — every layer caches
      8 of 8 layers × cache-per-layer = 8 units
    2. The D D D G D D D G schedule — only G layers cache
      2 of 8 layers × cache-per-layer = 2 units
    3. Cache ratio
      2 / 8 = 4× smaller cache than an all-attention stack of the same depth
    4. What the 6 D layers give up
      each D compresses history into a fixed-size state — no exact lookup of any single earlier token
    Answer 4× less KV cache, at the cost of only 2 layers per 8 that can read a specific earlier token directly
    That is the bet the whole timeline builds toward: most layers do not need exact recall, so pay for exact recall only where it earns its keep.
    Problem
    • Every mechanism above was published as a separate result. Nobody had shown what happens when you stack the recurrent-state line, the sparse-attention line and the positional-recalibration line into one model and train it end to end.
    • Frontier labs assemble these stacks behind closed doors, so the assembly decisions — how many attention layers, where, and what breaks without them — are rarely written down.
    Fixed
    • Publishes the assembly as an experience report: which growth steps preserve state, which fail silently, and what each layer type is actually for.
    • Holds three D layers per G layer at every scale, so the recurrent backbone carries most of the sequence work and sparse attention is bought only where exact recall is needed.
    • Borrows DroPE from Sakana and applies it at a scale Sakana's own paper did not reach.
    Cost
    • Six of every eight layers cannot look up a specific earlier token at all — they only see the fixed-size state. That is a real recall ceiling, not a tuning detail.
    • Trained and evaluated at 4K and 8K only. The paper is explicit that the longer context reaches were not tested, so the long-context claim is a direction, not a result.
    • It is a single-node systems report, not an independently replicated architecture study. Treat the layer ratio as one worked example of assembly, not as evidence that this particular ratio is optimal.
    When to choose this shape
    • When the workload is long and mostly sequential — summarising, drafting, streaming — and exact retrieval of one specific distant token is rare.
    • Not when the job is needle-in-a-haystack retrieval over a huge context: that work lands entirely on the 25% of layers that can still do it.
    • Not when you need a reproducible published baseline — for that, the hybrid models in the closing section below have far more scrutiny behind them.
    Hands to →
    • Nothing, yet — this is the end of the dated timeline, and the argument it closes on is still live.
